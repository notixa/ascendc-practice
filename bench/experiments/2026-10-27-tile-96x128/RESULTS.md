# 实验 2 — BLOCK_Q 64→96（迭代数 2048→1376）✅ 成功，采纳

## 假设

系统是 BAR-bound（Cube 只占 ~10%），所以**迭代数越少越快**，哪怕 tile 变大、总 MAC 变多。
按 UB 预算搜到 `BQ=96, BK=128`：

| BQ | BK | q | k | v | s | o | 总计 | N=4096 迭代 |
|---|---|---|---|---|---|---|---|---|
| 64 | 128 | 16 | 32 | 32 | 32 | 32 | 144 KB | 2048 |
| **96** | **128** | 24 | 32 | 32 | 48 | 48 | **184 KB** | **1376** |
| 128 | 128 | 32 | 32 | 32 | 64 | 64 | 224 KB ✗ | 1024 |

选 96/128 而不是 128/96 的关键：**`EVEN_K = N%128==0` 保持 True**，
循环体内没有 padding mask；`EVEN_Q=False` 只影响每 task 一次的 q load。

## 改动

`base_tile()` 删除，硬编码 `BLOCK_Q, BLOCK_K = 96, 128`；`HEAD_DIM=head_dim`。

## 测量

`bench/bench_fa.py --only triton --mode both`，warmup=10 / iters=50 / repeats=5，中位数。

## 结果

| case | 基线 (ms) | 96/128 (ms) | 提升 | TFLOPS 前→后 |
|---|---|---|---|---|
| full N=512 | 0.439 | 0.464 | — (地板) | 2.4 → 2.3 |
| full N=1024 | 0.461 | 0.498 | — (地板) | 9.3 → 8.6 |
| full N=2048 | 0.744 | **0.605** | **1.23×** | 23.1 → 28.4 |
| full N=4096 | 2.860 | **2.281** | **1.25×** | 24.0 → 30.1 |
| full B4 N=2048 | 2.879 | **2.299** | **1.25×** | 23.9 → 29.9 |
| causal N=2048 | 0.456 | 0.454 | **0%** (地板) | — |
| causal N=4096 | 1.550 | **1.262** | **1.23×** | 22.2 → 27.2 |
| causal B4 N=2048 | 1.626 | **1.380** | **1.18×** | 21.1 → 24.9 |
| `max_err` | ~1e-4 / ~1e-3 | **不变** ✓ | | |

**causal/full = 1.262/2.281 = 0.553**（理论块数比 0.508）✓

## 成本模型（重要，可直接预测下一步）

每次迭代成本随 tile 线性增长：

```
t/iter = A + B × (BQ·BK / 8192)
3.53 = A + 1.00 B
4.15 = A + 1.50 B        → A = 2.31 µs（同步/固定）, B = 1.23 µs（tile 比例）
```

因为 `迭代数 × tile ≈ 总工作量 = 常数`，B 项总量恒定，所以：

```
总时间(µs) = 2.31 × (每核迭代数) + W
```

| 配置 | 每核迭代 | 模型预测 | 实测 |
|---|---|---|---|
| 64/128 | 819 | 2894 µs | 2894 ✓ |
| 96/128 | 550 | 2273 µs | 2281 ✓ (误差 0.4%) |

**W(N=4096 full) ≈ 1002 µs = 68 TFLOPS 的纯计算当量 —— 这是 tile 放大的天花板。**

预测 **128×128**：`410×2.31 + 1002 = 1949 µs` → 再快 **1.17×**（比基线 1.48×）。
前提是把 UB 从 224KB 降到 ≤192KB（`o` 改 fp16）。

## 结论

**采纳。** 迭代数从 2048 降到 1376，full 1.25×、causal N=4096 1.23×，`max_err` 不变。

## 发现的问题（下一步优先级因此改变）

`causal N=2048 = 0.454 ms` ≈ **Triton Python launcher 的 ~0.44 ms 地板** → 该点已不是 device-bound。
`full N=512 = 0.464 ms` 同理（预测 device 仅 ~0.06 ms）。

**⇒ 小/中 case 的瓶颈已从 kernel 转移到调度开销。**
